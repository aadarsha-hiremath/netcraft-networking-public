# Phase 1 networking engine

## TCP

`connect_tcp` accepts a hostname, IPv4 address, or IPv6 address and a port from 1 through 65535.
It uses the system resolver for hostnames and requests a numeric-only lookup for IP literals.
It attempts up to eight distinct resolved endpoints in resolver order under one socket deadline.
Each failed socket closes before the next attempt. The first success ends the probe and
closes the socket without sending application data. If all attempts fail, the result reports
the last socket failure or a deadline expiration.

A pending TCP connect is checked for socket readiness, followed by `SO_ERROR`. Winsock can
signal a failed connect through the exceptional readiness set. The recorded `connect_ns` starts
immediately before the successful address attempt and ends after the OS confirms completion.
Resolution and failed address attempts contribute to total duration. The three-way TCP
handshake is distinct from ICMP echo and from a response generated by an application.
[Python socket API](https://docs.python.org/3.12/library/socket.html)
[Winsock select](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-select)

`echo_tcp` accepts a nonempty binary payload up to 4,096 bytes on loopback. The client sends the
payload and half-closes its write side. The server collects the stream through EOF, then writes
the echo and closes. The client validates the returned bytes and completes the measurement at
EOF. Closing before all expected bytes arrive is reported as a remote closure. Different bytes
or a stream longer than expected produce an unexpected-response error.

## UDP

`send_datagram` submits one datagram. `exchange_datagram` additionally waits for one datagram
from the selected peer using the same local socket. The OS associates the UDP socket with
that peer to select the destination and filter incoming datagrams by source address and port.
The association exchanges no handshake packets. The client accepts zero-length datagrams and
caps payloads at 65,507 bytes. The lab echoes datagrams up to 4,096 bytes.

Once a datagram has been sent, NetCraft waits within the remaining deadline without resending.
Firewalls, remote service behavior, routing, and packet loss can all cause silence. A receive
timeout describes that observation. Some systems surface an ICMP port-unreachable response as
a socket error. On Winsock, UDP receive error `WSAECONNRESET` is reported as a refused destination.
[Winsock recv](https://learn.microsoft.com/windows/win32/api/winsock/nf-winsock-recv)

## Timing and results

Each immutable result has an operation, protocol, target, port, UTC start and finish timestamps,
monotonic duration, and either success details or a classified error. The UTC values are wall
clock timestamps and can shift when the system clock changes. Elapsed measurements use
`perf_counter_ns()`. The result duration includes validation, resolution, socket I/O, and socket
cleanup. A successful exchange has a separate measurement from just before the first write
through the complete reply. UDP has no handshake measurement.

The socket deadline starts after resolution. A TCP echo or UDP request/reply shares the remaining
budget across connection or peer association, sending, and receiving. Values above zero and up to
60 seconds are accepted. Readiness waits and the time needed to resume a thread depend on OS
timer resolution and scheduling, so an observed timeout can exceed the configured interval.

Errors include the stage, a short message, and the OS error code when available. Validation and
missing hostname answers have distinct categories. Other categories cover refusal, timeout,
closure, unreachability, permissions, cancellation, and unexpected socket or response behavior.
Library callers get result objects for expected failures. Realized peer addresses, timings, and
response bytes are carried by success results. `NetworkResult.to_dict()` supplies JSON-ready
fields and a lossless Base64 representation for bytes.

## Execution and cleanup

The protocol APIs are synchronous by design. `DiagnosticRunner` keeps callers responsive by
handing work to a bounded group of threads, defaulting to four and accepting at most sixteen.
It rejects a new submission when all slots are occupied and returns a standard
`Future[NetworkResult]` for accepted calls. A GUI should dispatch the completion to its own
event loop before updating widgets. The standard library worker pool isolates the blocking OS
hostname resolver and keeps the socket APIs usable from a CLI or a future GUI.

```python
from netcraft.core.execution import DiagnosticRunner
from netcraft.protocols.tcp import connect_tcp

with DiagnosticRunner(max_workers=2) as runner:
    future = runner.submit(lambda token: connect_tcp("127.0.0.1", 8000, cancel=token))
    result = future.result()  # Wait only in a context where blocking is acceptable.
    print(result.to_dict())
```

A cancellation token uses a socket pair to wake a blocked readiness wait without polling.
Direct calls can share a caller-owned token whose context stays open until those calls finish.
Runner shutdown cancels outstanding cooperative calls and joins its workers. Run that join
off the UI thread when shutdown must stay responsive. Python's system `getaddrinfo()` call
cannot be interrupted by the token. Cancellation takes effect when that lookup returns, so
resolver duration can delay runner shutdown. There is no separate resolver thread to abandon.

Each echo fixture binds an ephemeral port to an explicit loopback address. A fixture owns
one worker and wakes it on teardown, even when the test body raises. A TCP fixture handles
one client at a time with a bounded read/write deadline. The silent fixture reads a request
and withholds its reply so tests can isolate the receive deadline.

## Verification and benchmarks

Tests use OS-assigned ports and keep hostname resolution local or substitute a controlled
resolver. IPv6 cases skip if the platform lacks IPv6 loopback. A fake pending connect makes the
TCP timeout test deterministic. Live loopback tests verify refusal, echoed bytes, receive
timeouts, cancellation, repeat operations, thread joins, and released ports. CLI tests run in
subprocesses with hard timeouts. An isolated import test rejects any attempted socket creation,
lookup, or thread startup.

The loopback benchmark warms up the fixture, then samples successful TCP handshakes and UDP
echoes sequentially. It also measures the total observed duration of ten silent UDP attempts.
It reports median and nearest-rank p95. A separate `tracemalloc` pass compares retained and peak
Python allocations after warm-up. Those figures exclude kernel buffers and native allocations.
The script checks for remaining fixture workers on exit. Results vary with host load, OS timer
resolution, and Python version. They describe the local machine and its loopback path.

## Phase 3 integration

Monitoring calls the same protocol entry points through `monitoring/probes.py`, which copies
only telemetry fields into immutable observations. `monitoring/scheduler.py` owns cadence and
worker lifetimes, and its coordinator thread writes history. SQLite persistence, query analytics,
and streaming export sit behind distinct modules. CLI commands consume those modules directly.
A future GUI can reuse them and marshal updates to its own event loop.
